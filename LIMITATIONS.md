# Допущения, ограничения и план развития

## 1. Допущения модели

### 1.1. Параметры трамвая
- Масса: **38 000 кг** («линейный») или **30 000 кг** («пустой») — переключается
  параметром `vehicle.profile`.
- Эффективный радиус колеса: **0.30 м** (постоянный, износ не моделируется).
- Расстояние между осями вращения тележек: **7.55 м** (по данным организаторов).
- Базлайн антенн GNSS (master → rover): **12.436 м** (TF: master (−9.873, 0, 3.0),
  rover (2.563, 0, 3.0)).
- Все 4 колеса ведущие.
- Передаточное отношение редуктора: 1.0 (прямой привод).

### 1.2. Характеристика тягового привода
- Кусочно-линейная аппроксимация моментной характеристики по 8 точкам.
- Максимальное тяговое усилие: **90 кН**, тормозное: **120 кН**.
- Номинальная мощность: **300 кВт** (ограничение постоянной мощности).
- Инерционность привода моделируется фильтром первого порядка с τ = 0.20 с.
- Точные тяговые характеристики производителем не предоставлены — параметры
  подобраны по телеметрии.

### 1.3. Сопротивление движению
- Сопротивление качению: `c_rr = 0.0060` (адаптируется онлайн).
- Аэродинамическое: `Cd·A = 12.0 м²` (оценка для трамвая).
- Сопротивление на кривых: пропорционально кривизне с `k_curve = 0.0015`.
- Уклон берётся из карты маршрута. Без карты — уклон считается нулевым.

### 1.4. Сцепление колесо-рельс
- `μ_peak = 0.22` — сталь по стали, сухой рельс.
- `μ_wet = 0.22 × 0.65 = 0.143` — мокрый рельс (множитель не применяется
  автоматически — переключение вручную).
- Кривая сцепления — модель Pacejka.
- `μ` адаптируется онлайн по рассогласованию тягового усилия и ускорения
  в установившемся режиме.

### 1.5. Одометрия и проскальзывание
- Датчики скорости колёс — тахометры (тип не уточнён организаторами).
- VelocitySensor.velocity в bag-записях — **км/ч** (эмпирически подтверждено).
- Проскальзывание детектируется 5 независимыми тестами на основе сравнения
  измеренной и модельной динамики.

### 1.6. GNSS
- GNSS доступен только в первые несколько секунд записи (гарантировано
  организаторами).
- Качество GNSS не гарантировано — все обновления после инициализации строго
  gated (отбрасываются при расхождении с модельной оценкой > порога).
- GNSS не используется как основной источник скорости или положения.

### 1.7. Карта маршрута
- Маршрут един для всех прогонов (Щукинская ↔ Таллинская).
- Карта построена офлайн по обучающим прогонам (4710 точек в UTM).
- При отсутствии карты положение вычисляется счислением вдоль начального курса.

### 1.8. Система координат
- Выходное положение — локальная метрическая СК (MGRS/UTM минус начало записи).
- Оси: X — вперёд (восток), Y — налево (север), Z — вверх (REP-103).
- Высота — эллипсоидальная WGS84 (не над геоидом).

## 2. Конфигурируемые параметры

Все параметры — в `cpp/tram_odometry/config/params.yaml` (216 строк), сгруппированы:

| Группа | Ключевые параметры |
|--------|-------------------|
| `topics` | Имена всех входных/выходных топиков |
| `rates` | Частота публикации (50 Гц), diagnostics (2 Гц) |
| `frame` | Режим координат (mgrs_relative/absolute/enu_local), UTM-зона |
| `gnss` | Базлайн антенн, пороги отбрасывания, порог калибровки (30 м) |
| `vehicle` | Масса, радиус колеса, колёсная база, передаточное число |
| `traction` | Кривая момент/ход, предельные усилия, мощность, инерционность |
| `dynamics` | Коэффициенты сопротивлений, источник уклона |
| `adhesion` | Параметры кривой Pacejka, пороги рассогласования тележек |
| `filters` | Окна Hampel/ФНЧ, порог зависания/пропуска |
| `observer` | Шумы процесса/измерений, гейт χ², окно инициализации GNSS (2.5 с) |
| `ml` | Включение ML, модель, пределы поправок, watchdog |
| `path_map` | Файл карты, порог загрузки (200 м), радиус поиска |
| `runtime` | Бюджет цикла (10 мс), длина истории |

## 3. Ограничения решения

### 3.1. Известные технические ограничения
1. **ML-корректор: 16 признаков.** Контракт с Python-стороной определяет
   20 признаков для slip gate; C++ использует собственный 16-признаковый
   контракт. Два набора несовместимы.
2. **Slip gate не интегрирован.** GBDT-модель `slip_gate.json` (200 деревьев)
   не разбирается в C++ — slip-детектор чисто физический.
3. **Скоростной корректор ML отключён.** Валидация показала, что коррекция
   масштаба (`log_scale`) и сцепления (`mu`) ухудшает RMSE — выходы модели
   обнулены.
4. **Калибровка `b_scale` только по GNSS.** Без GNSS масштаб одометрии остаётся
   равным 1.0, что вносит систематическую ошибку ~3% в положение.
5. **Карта только для одного маршрута.** Заезды в депо/на пути отстоя
   не поддерживаются.
6. **Счисление без карты** накапливает ошибку на кривых (нет информации
   о направлении после потери GNSS).

### 3.2. Точность
| Метрика | Значение | Примечание |
|---------|----------|------------|
| MAE скорости | 1.23 м/с | 2001 семпл, полный прогон |
| Медианная ошибка скорости | 0.15 м/с | переходные режимы ухудшают среднее |
| P90 ошибки скорости | 3.70 м/с | |
| ML RMSE (a_residual) | 0.375 м/с² (moving) | 6.6M строк, 5-fold CV |
| Улучшение ML vs baseline | 4.6× | baseline RMSE = 1.038 м/с² |

Данные по точности положения — в процессе сбора (требуют запуска чекера).

### 3.3. Производительность
- Частота публикации: **50 Гц** (≥ 10 Гц по ТЗ).
- Бюджет цикла: **≤ 10 мс** (задержка «вход → результат» ≤ 100 мс).
- ML-вывод: ≤ 2 мс на вызов (watchdog отключает модель при превышении).
- 42 модульных теста (C++), 77 тестов (Python) — все проходят.
- Ресурсы: ≤ 2 ядра, ≤ 0.5 ГБ ОЗУ (соответствует требованиям).

## 4. План развития после хакатона

### 4.1. Краткосрочные улучшения (1–2 недели)
- [ ] Интеграция slip_gate.json (200-дерево GBDT) как дополнительного детектора.
- [ ] Унификация 16- и 20-признакового контрактов.
- [ ] Запуск чекера и получение метрик точности положения.
- [ ] Исправление калибровки `b_scale` для прогонов без GNSS.
- [ ] Добавление onnx-рантайма для более сложных ML-моделей.

### 4.2. Среднесрочные улучшения (1–2 месяца)
- [ ] Адаптивная оценка массы трамвая по телеметрии.
- [ ] Модель износа колеса (дрейф радиуса).
- [ ] Поддержка нескольких маршрутов / заездов в депо.
- [ ] Интеграция официальной карты от организаторов (вместо построенной офлайн).
- [ ] Улучшение счисления: фильтр частиц для мультимодальной неопределённости
      положения.

### 4.3. Долгосрочные улучшения (3–6 месяцев)
- [ ] Перенос на реальное железо (архитектура ARM, hard real-time).
- [ ] Интеграция с остаточным EKF автопилота для слияния с другими датчиками
      (лидар, камера) при их доступности.
- [ ] Обучение на расширенном датасете с покрытием всех сезонов.
- [ ] Формальная верификация гарантий безопасности (пределы ошибки
      в наихудшем случае).
